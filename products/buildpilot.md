# BuildPilot

**Governed AI Software-Development Workspace**  
Controlled Execution | Evidence Review | Verification | Human Acceptance | Handoff

---

## Overview

**BuildPilot** is a governed AI software-development workspace designed to help software teams, product builders, agencies, and solo developers move from project intent to controlled execution, evidence review, verification, acceptance, and handoff.

BuildPilot is not positioned as a coding model.

It is a governance and execution workspace for AI-assisted software delivery.

The purpose of BuildPilot is to bring structure, truth, control, evidence, and human authority into AI-assisted development.

---

## Core Positioning

BuildPilot exists because AI-assisted software development is becoming powerful, but many teams still struggle with control.

AI tools can generate code, but software delivery also needs:

- Clear project intent
- Current-state understanding
- Scope discipline
- Execution boundaries
- Human confirmation
- Runtime visibility
- Evidence collection
- Verification
- Acceptance rules
- Handoff documentation

BuildPilot is designed to support these missing layers.

---

## Doctrine

BuildPilot is built around five core principles:

- **Truth before automation**
- **Governance before execution**
- **Evidence before acceptance**
- **Human authority over irreversible actions**
- **Controlled execution instead of blind automation**

These principles guide how BuildPilot approaches AI-assisted software delivery.

The goal is not to remove the human from development. The goal is to give the human better control over AI-assisted execution.

## BuildPilot Lifecycle

BuildPilot is organized around a governed delivery lifecycle.

### 1. Discovery

The system begins by understanding the project, its purpose, and the user’s goal.

### 2. Current-State Review

Before execution begins, BuildPilot considers the existing project state instead of assuming a blank slate.

### 3. Human Confirmation

Important direction and irreversible steps require human authority.

### 4. Governance Registration

The project is brought into a governed workspace where execution can be tracked and controlled.

### 5. Intent Capture

BuildPilot captures what the user actually wants to achieve before tasks are generated.

### 6. Scope Definition

The work is converted into clear boundaries so execution does not drift.

### 7. Readiness Checks

The project is checked for readiness before execution begins.

### 8. Roadmap Planning

The system supports phased planning so work can move in a structured way.

### 9. Execution Contract

Execution is governed by a clear contract covering what should happen, what should not happen, and what evidence is required.

### 10. Bounded Tasks

Work is broken into bounded tasks that can be executed, reviewed, and accepted.

### 11. Controlled Execution

Execution is controlled rather than blindly automated.

### 12. Evidence Generation

BuildPilot emphasizes evidence before acceptance. Work should produce visible proof of what changed and whether it passed.

### 13. Verification

Completed work must be verified against expectations.

### 14. Human Review

The human remains the final authority for acceptance and decision-making.

### 15. Acceptance

Work is accepted only after review and evidence.

### 16. Handoff

The system supports handoff so the state of the project is clear after execution.

## Runtime Experience Direction

A major BuildPilot focus is runtime experience.

When AI-assisted execution is happening, users should not be left blind.

The runtime experience direction includes:

- Live progress visibility
- Adapter status
- Execution state changes
- Runtime result recording
- Elapsed time visibility
- Timeout awareness
- Evidence visibility
- Dashboard-level execution status
- Clear success, failure, or review-needed outcomes

This matters because a governed workspace should not only start execution. It should help the human understand what is happening while execution is running.

---

## Evidence and Verification

BuildPilot treats evidence as a first-class part of software delivery.

A task should not be considered complete just because code was generated.

A task should be supported by evidence such as:

- Files changed
- Tests run
- Commands executed
- Result summaries
- Failure messages
- Runtime logs
- Verification outcome
- Manual review notes
- Acceptance status

This supports the principle:

> Evidence before acceptance.

---

## Human Authority

BuildPilot keeps human authority central.

The system is designed so that humans remain responsible for:

- Approving direction
- Confirming scope
- Reviewing evidence
- Accepting or rejecting execution results
- Deciding whether to continue
- Controlling irreversible actions
- Guiding final delivery

BuildPilot is not designed to remove the human from software delivery.

It is designed to help the human govern AI-assisted software delivery more effectively.
